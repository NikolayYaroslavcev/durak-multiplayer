# План разработки: Mini Multiplayer Game Platform («Дурак»)

Тестовое под вакансию: React/TypeScript/Node.js программист, игровая платформа.

**Концепция:** не «игра ради игры», а каркас платформы (lobby → matchmaking → комната → игра), где первая реализованная игра — упрощённый «Дурак». Архитектура спроектирована так, чтобы `game-core` не зависел от React/Phaser/NestJS и мог использоваться другим клиентом (в т.ч. мобильным) в будущем.

**MVP поддерживает ровно двух игроков.** Поддержка 3+ игроков не входит в MVP и не добавляется (см. `docs/architecture-research.md`, разделы 2 и 4).

### Архитектурные принципы (закреплены по итогам Research & Architecture)

**Server-authoritative:**
- Полный `GameState` существует только на сервере.
- Клиент отправляет намерение (`action`), а не новый state.
- Сервер самостоятельно валидирует каждое действие (не доверяет клиенту).
- Сервер применяет действие через `game-core` (`getValidMoves` + `applyMove`).
- Клиент получает результат только после того, как сервер обработал действие (никаких оптимистичных обновлений на клиенте).

**Hidden state:**
- Клиент никогда не получает полный `GameState`.
- Сервер использует `toClientView(state, playerId)` как единственный канал раскрытия состояния.
- Собственные карты игрока отправляются полностью.
- Карты соперника не отправляются — только их количество.
- Порядок карт в колоде клиенту не раскрывается.

**Три сценария, которые обязаны работать без костылей — это ядро оценки:**
- [ ] Player A → Find opponent → matchmaking → Player B → игра началась
- [ ] Игрок пытается сходить не в свой ход / чужой картой → сервер отклоняет
- [ ] Disconnect → reconnect → игрок получает актуальный per-player state и продолжает

## День 1 — `game-core`: правила игры без сети и без UI

**Цель дня:** `npm test` зелёный, вся логика работает в изоляции.

### Типы
- [ ] `Card` (suit, rank)
- [ ] `PlayerId`, `PlayerHand` — ровно 2 игрока (MVP, см. вводный раздел плана)
- [ ] `TableState` (карты в атаке/отбое)
- [ ] `GameStatus` — дискриминированный union, а не `PlayerId | null`: `{ phase: 'in_progress'; attackerId; defenderId }` | `{ phase: 'finished'; result: 'win'; winnerId }` | `{ phase: 'finished'; result: 'draw' }`
- [ ] `GameState` (игроки, козырь, колода, стол, `status: GameStatus`)
- [ ] `Move` — union-тип: `attack`, `defend`, `takeCards`, `endAttack` (вместо неоднозначного `pass`: `endAttack` — действие атакующего «закончить подкидывать», `takeCards` — действие защищающегося «беру карты»)

### Фиксированные правила (упрощённая версия — без переводного хода)
- [ ] Раздача карт (36 карт, по 6 на игрока, козырь определяется последней картой колоды)
- [ ] Лимит подкидывания зафиксирован явно: разрешены только ранги, уже присутствующие на столе; не больше 6 карт за раунд; не больше карт, чем в руке защищающегося на начало раунда
- [ ] `getValidMoves(state, playerId): Move[]` — какие ходы доступны игроку сейчас (для защищающегося `takeCards` доступен всегда при наличии неотбитой карты на столе, `endAttack` для атакующего доступен только когда на столе нет неотбитых карт)
- [ ] `applyMove(state, move): GameState` — чистая функция, возвращает новое состояние, не мутирует вход; обновляет `status` (включая переход в `finished`/`win`/`draw`) как часть перехода
- [ ] **Ключевая функция:** `toClientView(state, playerId): ClientGameState` — фильтрует состояние: свои карты полностью, карты соперника — только количеством (`opponentCardCount`), порядок карт в колоде не раскрывается (только `deckCount`)
- [ ] `game-core` не зависит от React, Next.js, Phaser, NestJS, Socket.IO, PostgreSQL, Redis — единственная реализация игровых правил, переиспользуемая server'ом (authoritative validation/transitions) и опционально web-клиентом (только UX-подсказки через `getValidMoves`, не как источник истины)

### Тесты (jest/vitest)
- [ ] Нельзя отбить младшей картой не козырем (невалидная защита)
- [ ] Взятие карт при невозможности отбиться
- [ ] Нельзя ходить не в свой ход (invalid turn)
- [ ] Нельзя сыграть карту, которой нет в руке (чужая карта)
- [ ] Невалидное подкидывание: ранг, которого ещё нет на столе
- [ ] Превышение лимита подкидывания (больше карт, чем в руке защищающегося, либо больше 6 за раунд)
- [ ] Действие после того, как `status.phase === 'finished'`, отклоняется
- [ ] Игра корректно завершается при опустошении руки одного из игроков (`win`)
- [ ] Ничья: колода пуста и оба игрока одновременно остались без карт
- [ ] `toClientView` не содержит карт соперника, только их количество; колода не раскрывает порядок карт (hidden state leakage)

**Критерий готовности дня:** вся логика покрыта тестами, ни одного импорта из React/Nest/Socket.IO в `game-core`.

## День 2 — Сервер: lobby, matchmaking, realtime, валидация, reconnect

**Цель дня:** два клиента через wscat/Postman-сокеты играют партию целиком.

### Инфраструктура Nest
- [ ] Модуль `LobbyModule` — очередь на matchmaking (простой массив/Map в памяти, без Redis пока)
- [ ] Модуль `GameModule` — хранение активных игр (Map<roomId, GameState>)
- [ ] `GameGateway` (Socket.IO) — обработка событий

### События (задокументировать сразу как контракт)
- [ ] `join_queue` — игрок встаёт в очередь на поиск соперника
- [ ] `leave_queue` — игрок отменяет поиск соперника
- [ ] `match_found` — сервер нашёл пару, создаёт комнату, оповещает обоих
- [ ] `make_move` — клиент отправляет намерение (не state!): `{ type: 'attack', card }` / `{ type: 'defend', card, against }` / `{ type: 'takeCards' }` / `{ type: 'endAttack' }`
- [ ] `game_state_update` — сервер рассылает новый `ClientGameState` каждому игроку **персонально** через `toClientView`
- [ ] `reconnect` — клиент передаёт session-токен, получает актуальный state своей игры
- [ ] `opponent_disconnected` — уведомление второго игрока об отключении соперника
- [ ] `opponent_reconnected` — уведомление второго игрока о возвращении соперника
- [ ] `error` / `move_rejected` — сервер объясняет, почему action отклонён

Новых событий сверх этого списка не добавлять — набор закрыт под три критических сценария.

### Server-side validation (обязательно, не срезать)
- [ ] Сервер — единственное место, где `applyMove` реально исполняется; полный `GameState` существует только на сервере
- [ ] На каждый `make_move` сервер сам вызывает `getValidMoves` из `game-core` и сверяет с запросом (клиент не является источником истины)
- [ ] Отдельно проверяется: чей сейчас ход, принадлежит ли карта игроку
- [ ] Невалидный action → `move_rejected` с причиной, state не меняется
- [ ] Malformed payload (не проходит schema validation формы, например через zod/class-validator) отклоняется до вызова `game-core`

### Reconnect
- [ ] При подключении сокета выдаётся session-токен (привязка к playerId + roomId)
- [ ] При disconnect — активная игровая сессия сохраняется (комната и `GameState` не уничтожаются), ставится таймер grace period 60–120 сек
- [ ] Второй игрок получает `opponent_disconnected`
- [ ] При `reconnect` с валидным токеном — игрок возвращается в комнату и получает актуальный персональный `ClientGameState` через `toClientView`; второй игрок получает `opponent_reconnected`
- [ ] Forfeit-правило: если игрок не возвращается в течение grace period, а соперник активен — не вернувшийся проигрывает технически (`status` → `finished`/`win` сопернику), комната закрывается
- [ ] Если не возвращаются оба — комната закрывается без победителя

### Тесты (server, integration через gateway + socket.io-client)
- [ ] Malformed Socket.IO payload отклоняется
- [ ] `reconnect` с невалидным/просроченным токеном отклоняется
- [ ] `reconnect` в уже закрытую (finished и закрытую по TTL) игру отклоняется
- [ ] Полный сценарий disconnect → `opponent_disconnected` → `reconnect` в grace period → `opponent_reconnected` → игра продолжается
- [ ] Forfeit: истечение grace period без reconnect → технический проигрыш не вернувшемуся игроку

**Критерий готовности дня:** два wscat-соединения проходят полный путь: очередь → матч → несколько ходов → попытка невалидного хода отклонена → disconnect одного → reconnect → игра продолжается → определён победитель.

## День 3 — Клиент: Next.js + Phaser

**Цель дня:** играбельно в двух реальных вкладках браузера от начала до конца.

### Страницы Next.js
- [ ] `/` — Lobby: кнопка «Найти соперника», счётчик онлайн (опционально)
- [ ] `/game/[roomId]` — игровой экран

### Интеграция Phaser
- [ ] Обёртка `Phaser.Game` внутри React-компонента через `useEffect`, корректный `destroy()` при unmount
- [ ] Сцена: рука игрока снизу (кликабельные карты), карты соперника рубашкой вверх сверху (по количеству из state), стол по центру
- [ ] Индикатор: чей сейчас ход, оставшиеся карты в колоде

### Логика клиента
- [ ] Socket-клиент: подключение, обработка `game_state_update`, `move_rejected`
- [ ] Клик по карте → отправка `make_move` с намерением (не изменяет state локально до подтверждения сервера)
- [ ] Экран победы/поражения при завершении игры
- [ ] Обработка обрыва соединения: попытка `reconnect` при восстановлении сети (можно упростить — кнопка «Переподключиться»)

**Критерий готовности дня:** полная партия «Дурака» разыгрывается в двух вкладках без ручного вмешательства в код.

## День 4 (опционально, по остатку времени) — Полировка и бонусы

MVP не требует PostgreSQL или Redis: активные комнаты и matchmaking-очередь полностью работают in-memory (см. Дни 0–2). PostgreSQL, Redis и Docker — опциональные задачи ниже, они не поднимаются в приоритете выше трёх критических сценариев.

Делать **строго сверху вниз**, останавливаться там, где кончилось время:

- [ ] PostgreSQL + Prisma: таблицы `users` (можно anon/guest), `matches`, `match_players`, `game_actions` (лог ходов)
- [ ] Страница истории партий (кто выиграл, длительность)
- [ ] Redis: вынести туда matchmaking-очередь и активные комнаты вместо in-memory Map (демонстрирует готовность к горизонтальному масштабированию)
- [ ] Docker Compose: Postgres + Redis + оба сервиса поднимаются одной командой
- [ ] `README.md`: архитектурная схема, явный раздел про переносимость `game-core` на другой клиент (мобильный / другая игра)
- [ ] **Бонус-модуль:** второй пакет `game-core-grid` (Tactical Arena) — 3–4 юнита, сетка 8×8, без баланса, как доказательство, что архитектура платформенная, а не заточена под одну игру

## Что не жертвовать ни при каких условиях

1. Server-side validation каждого действия
2. Per-player hidden state (`toClientView`)
3. Reconnect с восстановлением состояния

Всё остальное (Postgres, Docker, история партий, бонус-арена) — жертвуется первым при нехватке времени.

## Приоритет сокращения, если время поджимает

Postgres/Docker → бонус-арена → полировка UI → (не трогать: validation, hidden state, reconnect)
