## 2. Requirements

### Обязательно (критично для оценки, "не жертвовать")
1. Server-side validation каждого действия.
2. Per-player hidden state (`toClientView`).
3. Reconnect с восстановлением персонального state.
4. Три сценария из плана должны проходить целиком:
   - matchmaking A → B → игра началась;
   - недопустимое действие отклоняется сервером;
   - disconnect → reconnect → продолжение с актуальным состоянием.

### Второстепенно (жертвуется первым)
Postgres/Prisma, история партий, Redis, Docker Compose, Tactical Arena, визуальная полировка Phaser.

### Потенциально избыточное для 3–4 дней
- Redis + Postgres + Docker + история + Tactical Arena одновременно — план сам это признаёт и явно откладывает в опциональный День 4 с порядком урезания. Это корректно, менять не нужно.
- Риск в другом месте: День 3 (Next.js + Phaser + полный протокол + reconnect UI) обычно недооценивается по времени. Рекомендация — держать Phaser-сцену максимально простой (статичные позиции, минимум анимаций), чтобы не тратить время в ущерб трём критическим сценариям.

### Неоднозначности, которые нужно снять до кодирования
- Число игроков нигде явно не зафиксировано. Matchmaking описан как поиск одного соперника (A → B), поэтому логично зафиксировать **строго 2 игрока** на MVP. Это резко упрощает state machine (нет множественных атакующих/подкидывающих). См. раздел 12.
- `Move` union включает `pass`, но не ясно, что это: у атакующего есть действие «закончить подкидывать» (стол уходит в бито), у защищающегося — `takeCards`. Если `pass` — это одно и то же действие для обеих ролей, оно перегружено смыслом. Нужно явно развести два действия. См. раздел 12.
- «без ограничений на подкидывание сверх базовых» — сама формулировка неоднозначна: базовые ограничения Дурака (макс. 6 карт на столе, не больше карт в руке защищающегося, только ранги, уже лежащие на столе) — это и есть основные правила, а не какое-то дополнительное сужение. Нужно зафиксировать точную формулу лимита (раздел 4).
- `checkGameOver(state): PlayerId | null` не различает «игра продолжается» и «ничья» (оба игрока одновременно остались без карт при пустой колоде) — оба случая попадают в `null`. См. раздел 12.

## 3. Proposed architecture

```
Client (Next.js + React + Phaser)
        │  Socket.IO client (тонкая обёртка/hook в React)
        ▼
Socket.IO Gateway (NestJS)
        │  делегирует use-case сервисам
        ▼
LobbyService / GameService  ──uses──▶  game-core (pure functions)
        │
        ▼
In-memory room store (Map<roomId, GameState>)
```

Ответственности:
- **game-core** — единственный источник правил игры. Чистые функции, детерминированные, без побочных эффектов и без сетевых/UI зависимостей.
- **GameService / LobbyService (NestJS)** — оркестрация: держат `GameState` в памяти, вызывают `game-core` для валидации и переходов, управляют жизненным циклом комнаты, matchmaking-очередью, reconnect-токенами и таймерами.
- **GameGateway (Socket.IO)** — тонкий транспортный слой: принимает события, парсит/валидирует форму payload (не игровые правила, а форму — например через class-validator/zod), вызывает сервисы, рассылает персональные `game_state_update`.
- **React/Next.js** — платформенный UI: lobby, роутинг, владение сокет-соединением, владение "последним полученным от сервера state".
- **Phaser** — только рендеринг и ввод (клик по карте → событие наверх), не содержит правил.

Источник истины — `GameState` на сервере. Клиент никогда не мутирует его напрямую; клиент отправляет **намерение** (`make_move`), сервер решает, применять ли его.

## 4. Game domain

### Решение: 2 игрока на MVP
Явно фиксируем 1v1. Это соответствует тому, как matchmaking описан в плане, и убирает необходимость в множественных атакующих/третьих игроках, что для 3–4-дневного тестового было бы избыточным риском.

### State
```ts
type Suit = '♠' | '♥' | '♦' | '♣';
type Rank = 6 | 7 | 8 | 9 | 10 | 11 /*J*/ | 12 /*Q*/ | 13 /*K*/ | 14 /*A*/;
type Card = { suit: Suit; rank: Rank };

type PlayerId = string;

type TableSlot = { attack: Card; defend?: Card };

type GameStatus =
  | { phase: 'in_progress'; attackerId: PlayerId; defenderId: PlayerId }
  | { phase: 'finished'; result: 'win'; winnerId: PlayerId }
  | { phase: 'finished'; result: 'draw' };

type GameState = {
  players: Record<PlayerId, { hand: Card[] }>;
  deck: Card[];               // оставшиеся карты, лицом вниз
  trumpSuit: Suit;
  trumpCard: Card;            // последняя карта колоды, видна всем
  table: TableSlot[];
  discardCount: number;       // сколько карт ушло в бито (для отладки/UI, не для правил)
  status: GameStatus;
};
```

### Move
```ts
type Move =
  | { type: 'attack'; playerId: PlayerId; card: Card }
  | { type: 'defend'; playerId: PlayerId; card: Card; against: Card }
  | { type: 'takeCards'; playerId: PlayerId }
  | { type: 'endAttack'; playerId: PlayerId }; // явно переименовано из "pass" — см. раздел 12
```

### Операции
- `createInitialState(playerIds: [PlayerId, PlayerId], rng: () => number): GameState` — 36 карт, перетасовка, раздача по 6, козырь = последняя карта колоды. `rng` инжектируется, чтобы тесты были детерминированными.
- `getValidMoves(state, playerId): Move[]` — единственный источник "что можно". Клиент может опционально использовать её же для UI-подсказок (см. раздел 7), но не для принятия решений вместо сервера.
- `applyMove(state, move): GameState` — чистая функция, всегда возвращает новый объект, никогда не мутирует вход. Бросает/возвращает ошибку с кодом причины, если move невалиден (сервис-слой обязан вызвать `getValidMoves`/валидацию до вызова, но `applyMove` тоже не должен доверять входу слепо).
- `checkGameOver` — не отдельная функция поверх `GameState`, а часть `status` внутри самого `GameState`, обновляемая внутри `applyMove` (после взятия/добора карт). Явно разводит "in_progress" / "win" / "draw" вместо `PlayerId | null`.
- `toClientView(state, playerId): ClientGameState` — фильтрация под конкретного игрока (раздел 6).

### Правила подкидывания (зафиксировано, чтобы снять неоднозначность плана)
Для 1v1, без переводного хода:
- Атакующий (attackerId) может доложить карту любого ранга, уже присутствующего на столе (в атаке или отбое текущего раунда), в любой момент, пока не объявит `endAttack`.
- Лимит одновременно лежащих на столе карт атаки за раунд: `min(6, defenderHand.length + tableUnresolvedCount)`, где на практике это сводится к стандартному правилу Дурака: нельзя доложить больше карт, чем осталось в руке защищающегося на момент начала раунда, и не больше 6 карт всего за раунд.
- Раунд заканчивается: `endAttack` от атакующего при отсутствии неотбитых карт на столе → все карты стола уходят в бито, оба добирают до 6 (атакующий первым); либо `takeCards` от защищающегося → все карты стола уходят защищающемуся в руку, атакующим следующего раунда остаётся тот же игрок, добор всё равно в порядке "нынешний атакующий → защищающийся".
- `takeCards` доступен защищающемуся **всегда**, даже если формально возможен `defend` — это выбор игрока, а не следствие невозможности отбиться. Валидный набор `getValidMoves` для защищающегося почти всегда включает `takeCards`, если на столе есть неотбитая карта.

### Конец игры
- Побеждает игрок, первым избавившийся от карт **при пустой колоде** (обычное правило "дурака" — кто остался с картами, тот проигравший; в 1v1 это симметрично "кто опустел первым — выиграл").
- Ничья: колода пуста и оба игрока одновременно остаются без карт после одного и того же розыгрыша (например оба отбили последние карты в одном раунде) — редкий, но обязателен к тестированию edge case.

## 5. Multiplayer model

### Комнаты и matchmaking
- `LobbyService` держит очередь (`PlayerId[]` или простой массив сокетов) в памяти.
- `join_queue`: игрок добавляется в очередь; если есть второй в очереди — сервис снимает обоих, создаёт `roomId`, вызывает `createInitialState`, кладёт `GameState` в `Map<roomId, GameState>`, эмитит `match_found` обоим персонально (в их сокет, не в комнату — до этого момента у них ещё нет общего socket.io room).
- После `match_found` оба сокета джойнятся в socket.io room `roomId` — дальше рассылка идёт через неё, но с персональным payload (см. ниже).

### Actions (жизненный цикл хода)
1. Клиент отправляет `make_move` с намерением (тип хода + карта), НЕ состоянием.
2. `GameGateway` проверяет форму payload (schema validation), передаёт в `GameService.handleMove(roomId, playerId, move)`.
3. `GameService` достаёт `GameState` из Map, вызывает `game-core.getValidMoves(state, playerId)`, сверяет запрошенный `move` с допустимыми.
4. Если невалиден → `move_rejected` только инициатору, state не меняется.
5. Если валиден → `applyMove` → новый `GameState` кладётся в Map → для каждого игрока комнаты вызывается `toClientView(state, playerId)` и отправляется `game_state_update` **персонально** (`io.to(socketId).emit(...)`, не broadcast в комнату), поскольку у игроков разные представления состояния.

### State synchronization
Сервер — единственный источник истины. Клиент не применяет оптимистичных обновлений локально (в явном соответствии с планом: "не изменяет state локально до подтверждения сервера"). Это осознанное упрощение — client-side prediction/rollback для карточной игры с ходами раз в несколько секунд не оправдывает сложность в рамках тестового.

### Disconnect / Reconnect
- При установке соединения в комнату игроку выдаётся session-токен (случайная строка), привязанный на сервере к `{playerId, roomId}`.
- При `disconnect` сокета: комната не удаляется, `GameState` остаётся в Map, игрок помечается `connected: false`, стартует таймер (60–120 сек), второй игрок получает `opponent_disconnected` (см. раздел 12 — предложенное дополнение к протоколу).
- При `reconnect` с валидным токеном: сервер находит `{playerId, roomId}`, привязывает новый `socketId`, отменяет таймер, отправляет `toClientView(state, playerId)` через `game_state_update`, второй игрок получает `opponent_reconnected`.
- Если таймер истёк, а один игрок не вернулся: второй побеждает по техническому поражению (форфейт), `status` переходит в `finished`, комната закрывается через небольшой TTL. Если истекли оба — комната закрывается без победителя.

### Завершение игры
`status.phase === 'finished'` — часть `GameState`, транслируется как обычный `game_state_update` (отдельного `game_over`-события не требуется, чтобы не дублировать источник истины — клиент реагирует на `status` внутри полученного state).

## 6. Hidden state

Единственный легальный канал раскрытия состояния — `toClientView(state, playerId)`, вызываемый на сервере перед каждой отправкой. Клиент никогда не получает сырой `GameState`.

```ts
type ClientGameState = {
  yourHand: Card[];                 // свои карты — полностью
  opponentCardCount: number;        // чужие — только количество
  deckCount: number;
  trumpCard: Card;                  // видна всем по правилам игры
  table: TableSlot[];               // карты на столе открыты всем по определению
  status: GameStatus;
  yourTurnRole: 'attacker' | 'defender' | null;
};
```

Гарантии:
- Карты соперника (`Card[]`) никогда не попадают в сериализуемый объект, отправляемый другому игроку — только число.
- Тест на это (раздел 9) должен проверять не "выглядит нормально", а буквально отсутствие объектов `Card` соперника в JSON-строке ответа.
- Поскольку `toClientView` — чистая функция в `game-core`, а не что-то, что собирается вручную в каждом хендлере gateway, риск "забыть отфильтровать в одном из мест" минимален: единая точка вызова.
- Deck — сервер никогда не сериализует порядок карт в колоде клиенту (только count), иначе через DevTools можно было бы вычислить будущие раздачи.

## 7. Client / server boundaries

| Слой | Отвечает за | НЕ отвечает за |
|---|---|---|
| Next.js | Роутинг (`/`, `/game/[roomId]`), layout, lobby-страница, серверные/статические части | Хранение игрового состояния, игровые правила |
| React (client components) | Owns Socket.IO connection (hook/context), owns последний полученный `ClientGameState`, matchmaking UI, экран победы/поражения, reconnect UI/баннер, передача данных в Phaser через тонкий bridge | Рендеринг карт как canvas-объектов, анимации |
| Phaser | Визуализация: рука снизу (кликабельна), карты соперника рубашкой вверх по количеству, стол по центру, индикатор хода/колоды. Эмитит наверх события клика | Валидация ходов, хранение "истинного" state, сетевые вызовы напрямую |
| Socket.IO client | Транспорт | Ничего игрового — только эмит/подписка на события |
| game-core (переиспользуется и в web, и в server) | Единственное определение правил: `getValidMoves`, `applyMove`, `toClientView`, `createInitialState` | Знание о сети, React, Phaser |
| NestJS (Gateway/Services) | Матчмейкинг, room lifecycle, session/reconnect, вызов game-core, единственное место, где `applyMove` реально исполняется | Дублирование правил — сервис лишь вызывает game-core, не переизобретает логику |

Важный принцип во избежание дублирования правил между Phaser и сервером: **game-core — общий npm-пакет**, импортируемый и `apps/web`, и `apps/server`. Если на клиенте нужна подсказка "какая карта сейчас играбельна" (подсветка), это делается вызовом той же самой `getValidMoves` из того же пакета — то есть кода правил не два, а один, используемый в двух местах чисто для UX-хинта. Авторитетное решение всё равно принимает только сервер; `move_rejected` — обязательный путь, а не fallback на случай бага. Для Дня 3 рекомендуется для простоты **не делать клиентскую подсветку сразу**, полагаться на `move_rejected`, и добавить хинты позже, если останется время — это не критический сценарий.

## 8. Persistence

| Технология | Нужна для MVP (3 критических сценария)? | Роль |
|---|---|---|
| In-memory (Map) | Да, полностью достаточно | `Map<roomId, GameState>`, matchmaking-очередь, `Map<sessionToken, {playerId, roomId}>` — всё это живёт в процессе Nest-сервера. Один процесс, без требования горизонтального масштабирования в тестовом. |
| PostgreSQL + Prisma | Нет | Полезна только для истории партий (День 4, опционально) — `users`(guest), `matches`, `match_players`, `game_actions`. Не нужна ни для одного из трёх критических сценариев. |
| Redis | Нет | Имеет смысл только если демонстрируется горизонтальное масштабирование (несколько инстансов Nest + Socket.IO Redis adapter для кросс-инстансной рассылки). Внедрение Redis без нескольких инстансов сервера — технология "для галочки", добавляет сложность (сериализация state, TTL, adapter) без демонстрационной ценности. Рекомендация: не делать, если явно не останется времени и желания показать этот конкретный навык; если делать — заявить об этом отдельно в README как "designed for, not required by MVP".
| Docker Compose | Нет | Полезен только если реально добавлен Postgres/Redis — иначе поднимать compose не для чего. |

Итог: MVP должен полностью работать без единой внешней БД. Это не срезание качества, а соответствие реальному объёму задачи (3–4 дня, single-instance demo).

## 9. Testing strategy

### game-core (чистые unit-тесты, jest/vitest, без сети)
- Раздача: 36 карт, по 6 на игрока, козырь = последняя карта колоды, детерминированность при фиксированном `rng`.
- `getValidMoves`: таблица случаев (можно/нельзя отбить, можно/нельзя подкинуть данный ранг, `takeCards` доступен всегда защищающемуся при наличии карты на столе, `endAttack` доступен только при отсутствии неотбитых карт).
- `applyMove`: чистота (не мутирует вход), корректные переходы для каждого типа move, ошибка/исключение на попытку применить невалидный move (defense-in-depth, даже если сервис уже отфильтровал).
- `checkGameOver`/`status`: победа, поражение, **ничья** (оба опустели одновременно), игра не завершается преждевременно.
- `toClientView`: сериализованный результат для игрока A не содержит ни одного `Card`-объекта из руки B — только `opponentCardCount`. Отдельно: колода не раскрывает порядок карт.

### Server (NestJS, integration через реальный gateway + socket.io-client в тестах)
- LobbyService: два клиента в очереди → ровно одна пара, комната создаётся один раз (защита от гонки при одновременном join).
- Полный сценарий 1: A и B находят друг друга → `match_found` у обоих → несколько ходов → игра завершается корректным победителем.
- Полный сценарий 2 (негативный, см. ниже).
- Полный сценарий 3: disconnect одного → GameState жив → `reconnect` с валидным токеном → `game_state_update` содержит актуальный персональный state → игра продолжается до конца.
- Reconnect timeout: с fake timers — истечение окна без reconnect → форфейт второму игроку.

### Негативные сценарии (обязательный список)
1. Ход не в свой ход (attacker пытается сходить, когда сейчас черёд defender, и наоборот).
2. Карта, которой нет в руке игрока.
3. `defend` картой, которая не бьёт атакующую карту и не козырь.
4. Подкидывание ранга, которого ещё нет на столе.
5. Подкидывание сверх лимита (больше карт, чем осталось в руке защищающегося, либо больше 6 карт в раунде).
6. `endAttack`, когда на столе есть неотбитая карта (нелегально — раунд не может завершиться так).
7. Любое действие после того, как `status.phase === 'finished'`.
8. `reconnect` с невалидным/просроченным токеном.
9. `reconnect` в комнату, которая уже закрыта.
10. Два одновременных сокета от одного и того же `playerId` (повторное подключение без явного disconnect) — нужно решить: либо отклонять новый сокет, либо считать это тем же кейсом, что reconnect (второй вариант проще и достаточен для MVP).
11. Клиент присылает `make_move` с типом/полями, не проходящими схему (malformed payload) — должно отклоняться на уровне валидации формы до game-core.

## 10. Risks and trade-offs

- **Неоднозначности правил (подкидывание, `pass`/`endAttack`, ничья)** — главный риск. Если не зафиксировать точные формулировки до Дня 1, велик шанс переписывать `game-core` в середине теста. Данный документ фиксирует конкретные решения (раздел 4) — рекомендуется закрепить их перед началом кодирования.
- **Число игроков не зафиксировано в исходном плане.** Решение зафиксировать 2 — осознанный trade-off: это несколько отступает от "полного" Дурака (где обычно 2–6 игроков и подкидывать могут все), но радикально снижает сложность state machine и полностью покрывает три критических сценария. Для сеньорского тестового это правильный компромисс: явно ограниченный, но чистый и полностью протестированный домен лучше, чем частично работающая N-игроковая версия.
- **In-memory state без персистентности** — рестарт сервера теряет все активные игры. Приемлемо для демонстрационного прототипа, должно быть явно задокументировано как известное ограничение (не "забытое"), а не решаться ради него самого добавлением БД.
- **Отсутствие аутентификации** — session-токен без привязки к реальному аккаунту теоретически можно перехватить и угнать reconnect. Для демо-скоупа это приемлемый риск; митигация — длинный случайный токен, короткий TTL комнаты после финиша.
- **Phaser/React lifecycle** — известный класс багов: `useEffect` + `Phaser.Game` при React StrictMode (двойной mount/unmount в dev) может создать два инстанса сцены или не вызвать `destroy()`. Требует аккуратного cleanup, стоит заложить время именно на это в День 3.
- **Недооценка Дня 3 по времени** — интеграция реального протокола + Phaser + reconnect UI в двух вкладках браузера — самая объёмная по интеграционным багам часть. Рекомендация — беречь этот день, не отвлекаться на визуальную полировку до прохождения трёх критических сценариев вживую.
- **Redis/Postgres как "for the résumé"** — если добавлять только чтобы упомянуть в списке технологий, это увеличивает объём кода и площадь для багов без демонстрационной пользы, конкурируя по времени с тремя критическими сценариями. Явно понижен приоритет (раздел 8), в согласии с самим планом.

## 11. Recommended implementation order

1. **День 0** — репозиторий, pnpm workspaces, структура папок, TS алиасы. (Без изменений от плана.)
2. **День 1 — game-core.** Сначала явно зафиксировать в коде (не только в этом документе) все решения из раздела 4: 2 игрока, точный лимит подкидывания, `endAttack` vs `takeCards`, дискриминированный `status` вместо `PlayerId | null`. Затем типы → `createInitialState` → `getValidMoves` → `applyMove` → `toClientView` → тесты. Опционально: после того как всё готово — мини-скрипт/CLI, симулирующий партию двумя вызовами game-core без сети, как дешёвая проверка до подключения Socket.IO (не обязательно, но снижает риск смешивания багов правил с багами протокола).
3. **День 2 — сервер.** `LobbyModule`, `GameModule`, `GameGateway`, все события протокола (включая предложенные дополнения из раздела 12), server-side validation, reconnect с таймером. Критерий готовности — как в плане: два wscat/socket.io-client соединения проходят все три сценария целиком, до Phaser дело не доходит.
4. **День 3 — клиент.** Next.js страницы, Socket.IO hook в React, Phaser-сцена (простая: статичные позиции карт, минимум анимаций), без клиентской предвалидации в первой итерации — полагаться на `move_rejected`. Клиентская подсветка играбельных карт — только если останется время.
5. **День 4 (опционально, строго по остатку времени, в порядке, уже заданном планом)** — Postgres/Prisma → история партий → Redis → Docker Compose → README с архитектурной схемой → Tactical Arena bonus.

## 12. Proposed changes to the current plan

Ничего в `plan-testovogo-zadaniya.md` не изменено — ниже только предложения с обоснованием.

1. **Зафиксировать 2 игроков явно.** План описывает matchmaking как поиск одного соперника, но нигде не пишет "игра только на двоих". Предлагается явно добавить это в раздел "Типы"/"Фиксированные правила" Дня 1 — иначе есть риск, что во время реализации кто-то попытается поддержать N игроков, что резко увеличивает сложность без пользы для трёх критических сценариев.

2. **Развести `pass` на два разных действия.** Текущий `Move` union включает единственный `pass`, но в игре есть два разных действия с похожим "ничего не делаю": атакующий объявляет конец подкидывания (стол уходит в бито) и защищающийся забирает карты. Второе уже есть отдельным `takeCards`. Предлагается переименовать/добавить `endAttack` для атакующего вместо перегруженного `pass`, чтобы `getValidMoves` не приходилось разбирать "что значит pass в данном контексте" по роли игрока.

3. **Точно определить лимит подкидывания.** Формулировка "без ограничений на подкидывание сверх базовых" неоднозначна. Предлагается явно записать формулу в Дне 1: разрешены только уже присутствующие на столе ранги, максимум 6 карт за раунд, не больше карт, чем в руке защищающегося на начало раунда.

4. **Заменить `checkGameOver(state): PlayerId | null` на дискриминированный результат.** Текущая сигнатура не различает "игра продолжается" и "ничья" — оба случая дают `null`. Предлагается либо сделать `status` частью `GameState` (как в разделе 4 этого документа) с явными вариантами `in_progress` / `finished(win, winnerId)` / `finished(draw)`, либо хотя бы поменять сигнатуру на `{ over: false } | { over: true; winnerId: PlayerId | null }` с явным комментарием, что `winnerId: null` при `over: true` означает ничью.

5. **Добавить `leave_queue` в список событий Дня 2.** У плана есть `join_queue`, но нет способа отменить поиск соперника. Для минимально приличного lobby UX (пользователь передумал/закрыл вкладку) стоит явно предусмотреть это событие, а не оставлять как забытый пробел.

6. **Добавить `opponent_disconnected` / `opponent_reconnected` в протокол Дня 2.** План описывает `reconnect` от вернувшегося игрока, но не уведомляет второго игрока о том, что партнёр отключился или вернулся. Без этого оставшийся в игре пользователь просто видит "зависшего" соперника без объяснения. Дешёвое дополнение, существенно улучшающее демонстрируемость reconnect-сценария.

7. **Явно прописать forfeit-правило.** План говорит "если оба игрока не возвращаются за отведённое время — комната закрывается", но не говорит, что происходит, если не возвращается только один, а другой ждёт. Предлагается явно зафиксировать: не вернувшийся в течение таймера при активном сопернике проигрывает технически (форфейт), после чего комната закрывается по обычной логике.

8. **Решить судьбу `shared-types` заранее, а не "если не поместится".** План оставляет это условным. Предлагается решить сейчас: игровые типы (`Card`, `GameState`, `Move`, `ClientGameState`) остаются в `game-core`; отдельный `shared-types` (или файл `protocol.ts` внутри `game-core`) нужен только для непровязанных с правилами игры контрактов — карта Socket.IO событий, `RoomId`, `SessionToken`, коды ошибок. Такое разделение также облегчает добавление второй игры в будущем: платформенный протокол переиспользуется, доменные типы — нет.

9. **Tactical Arena и остальной День 4** — план уже корректно ставит их в самый конец приоритетов и делает опциональными; в соответствии с ограничением задания (Tactical Arena не входит в обязательный MVP) изменений не требуется, только подтверждение текущего порядка.
